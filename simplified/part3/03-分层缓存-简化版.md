## 一句话核心

HiCache 把前缀缓存从 GPU 显存（L1）扩展到 Host 内存（L2）和可选外部存储（L3），用"跨层搬运 KV"换取"少重复计算相同前缀"，代价是恢复延迟与搬运带宽。

## 核心概念（只留能算账的公式）

- **为什么还不够**：Paged KV Cache 管显存分配/回收，前缀缓存避免相同前缀的重复计算，但两者都不能让有限的 GPU 显存无限保留历史。GPU 放不下时，HiCache 回答"能否先存别处，等需要再读回来"。
- **三层职责**：L1 = GPU 显存（命中直接算）；L2 = 本实例 Host 内存（先搬回 GPU）；L3 = 可选外部存储（先读 Host 再搬 GPU，配置共享存储时可跨实例复用）。越往下容量越大、恢复越慢。
- **恢复成本账**：`T_restore ≈ T_storage→Host + T_Host→GPU`。L2 命中无第一项，L3 命中两项都有。**只有 T_restore < 重算这段前缀的时间，复用才有直接延迟收益**。原文只用于理解的假设数字（非实测）：重算 200ms、Host 恢复 40ms → 划算；慢存储读 + 恢复 250ms → 不如重算。
- **复用前缀必须连续 + 状态就绪**：各层命中的 KV 要从请求开头连续接起来，不能中间缺一段跳段复用；L2/L3 的 KV 仍要搬回 GPU 才能参与计算。token 必须完全一致，文本"意思差不多"不能复用；system prompt/模板不同会改变可匹配前缀。
- **预取 prefetch**：请求 B 排队时先把它的 L3 缓存读到 Host，与请求 A 的 GPU 计算交叠。没读完时三种策略：`best_effort`（不等待，复用已就绪部分、其余重算）、`wait_complete`（等读完，争取更多复用但加等待）、`timeout`（限时等待后折中）。用户关心完整请求耗时，不是命中率。
- **按层恢复**：模型逐层执行，第 0 层 KV 就绪即可开始该层计算，同时继续搬后续层 KV，让搬运与计算交叠；但没有取消数据依赖，某层 KV 未到仍要等。

## 行业 Best Practice

- **先看重复前缀，再看容量压力**：多轮对话重复历史、围绕同一长文档反复问答、Agent 复用任务前缀 → 收益高。热点前缀长期留 L1 时下层收益有限；历史多、复用间隔长、GPU 容量不足时，L2/L3 才有机会补回命中。
- **开启 ≠ 更快**：命中率高不自动等于 TTFT 低。要算 restore vs recompute 的账，还要算备份成本——无差别备份"以后不再用"的前缀只是多写数据，白耗带宽与 Host 容量。
- **用服务指标验证**：`--enable-hierarchical-cache` 只开 GPU/Host 两层，不自动配共享 L3；Host 池大小、备份策略、存储接入要看版本对应的 HiCache 文档。对比时固定模型/请求分布/并发，重点看 TTFT、输入吞吐、尾延迟，同时观察各层实际复用 token 数、Host 占用、搬运负载。
- **现代背景**：全注意力 KV 之外，混合架构还要检查 SWA 窗口 KV、MAMBA 递归状态是否完整（Unified Radix Cache 处理）。
- **Failure mode**：只看命中率不看尾延迟（慢存储恢复拖垮 TTFT）；无差别备份浪费带宽；误以为 HiCache 能提高模型最大上下文长度或加速 decode——它只减少重复 prefill。

## 面试考点

1. **Q：已有前缀缓存，为什么还要分层缓存？**
   A：前缀缓存只在 GPU 上生效，GPU 显存有限，两次复用之间可能被驱逐；HiCache 把缓存扩展到 Host 和外部存储，用搬运换重复计算。Paged 管分配、前缀缓存管避免重复计算、HiCache 管"放不下先存别处"。
   追问：L2/L3 命中后还要做什么？→ 都要把 KV 搬回 GPU 才能参与计算，L3 还要先读到 Host。
   陷阱答案：说"HiCache 让命中永远免费"——命中不等于直接可用，恢复有搬运成本。

2. **Q：怎么判断一段前缀值得从下层恢复而不是重算？**
   A：比较 T_restore（L3 含 storage→Host + Host→GPU）与重算这段前缀的 forward 时间；只有恢复更快才有直接延迟收益。长前缀重算贵、慢存储读回来更贵，要实测带宽和计算速度。
   追问：命中率很高但 TTFT 没降，为什么？→ 可能恢复时间比重算还长，或备份/搬运开销把收益吃掉了。
   陷阱答案：拿原文的 200ms/40ms 当通用结论——那只是教学假设，必须实测。

3. **Q：prefetch 的三种策略怎么取舍？**
   A：`best_effort` 不等数据、已就绪部分复用其余重算，尽早执行；`wait_complete` 等读完争更多复用，但加等待；`timeout` 限时折中。长前缀重算贵时多等更划算，短前缀/存储拥堵时继续等会拖慢请求。
   追问：预取能隐藏多少延迟取决于什么？→ 排队窗口长度与存储读取能否在轮到该请求前完成。
   陷阱答案：说"预取越完整越好"——目标是最小化完整请求耗时，不是最大化命中率。

4. **Q：开启 HiCache 后命中率涨了但尾延迟变差，怎么排查？**
   A：查恢复路径（是否 L3 慢存储拖尾）、备份是否占带宽、预取策略是否让请求空等、各层复用 token 是否真的转化为 TTFT/吞吐改善。可能命中多但 restore 比重算慢，或搬运链路拥堵。
   追问：什么场景根本不该开？→ 几乎无相同前缀、输入短、搬运链路已拥堵时，加缓存容量未必改善延迟。
   陷阱答案：把"命中率"当最终目标——最终要看 TTFT、输入吞吐、尾延迟。
