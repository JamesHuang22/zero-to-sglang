## 一句话核心

Attention 公式只是数学定义；attention backend 是"模型算出的 QKV + 请求元数据 + KV Cache"与具体 GPU kernel 之间的适配层，负责把一次 Attention 组织成能在当前硬件上高效执行的实现。

## 核心概念（只留能算账的公式）

- **三个易混概念**：Attention **机制**（模型结构，MHA/GQA/MLA）、Attention **kernel**（一段具体 GPU 程序，分块矩阵乘 + 融合 softmax）、Attention **backend**（引擎准备输入、选合适 kernel 的那层适配）。换 backend 不改变模型结构/参数，只是换执行方式，但仍要验证数值精度。
- **Attention 数学式**：`O = softmax(QKᵀ/√d_h + M)V`。Q 是当前 Query，K/V 是可见历史，M 是因果掩码等约束，d_h 是头维。这只是数学关系，不含"数据怎么搬、任务怎么分"。
- **朴素实现的内存账**：完整分数表是 n×n。原文以 32k 序列、单层单头、每元素 2 字节估算：约 1.07×10⁹ 个分数 → 一张表约 2GiB，写出再读回一次就搬约 4GiB，还没算 softmax 权重。**瓶颈在"搬"中间矩阵**，不在算。
- **FlashAttention 两条直觉**：①分块——把小块 Q/K/V 搬进片上 SRAM 就地算，中间结果用完即弃；②边算边归一化（online softmax）——记"当前总权重 + 累积输出"两笔账，新块加入后按比例重调旧输出再合并，让完整 S/P 矩阵从头到尾不写回 HBM。**省的是中间矩阵的 HBM 搬运，计算量仍是 O(n²)，没有变线性。**
- **split-KV**：decode 阶段 Query 很少、GPU 并行不够，把长 KV 拆成多段并行算局部结果，再合并各段 softmax 归一化信息。增加并行度，但引入局部结果存储与合并开销；上下文短或 batch 已大（利用率已饱和）时拆更多未必更快。

## 行业 Best Practice

- **先筛兼容，再谈性能**：确认模型是 MHA/GQA 还是 MLA、GPU 架构、KV dtype、是否启用滑动窗口/投机解码。一个单独测试里很快的 kernel，若不支持线上功能就跑不起来。
- **四个主流 backend 定位**：
  - **FlashInfer**：面向推理服务的 kernel 库，处理变长请求 + 分页 KV，Plan（组织任务/split-KV/复用计划）与 Run（逐层执行）分离；优势是服务适配完整，代价是元数据与计划有开销。
  - **Triton**：写 GPU 程序的编译器（接近 Python 语法），SGLang 的 triton 后端是"用 Triton 写的一组 Attention 实现"；优势是易读易改易扩展，代价是性能依赖编译与调优、首次编译有启动成本。
  - **FA3**：在分块 Attention 上利用 Hopper 的 TMA + WGMMA 做异步流水线，让搬运/矩阵乘/softmax 交叠；硬件与形状限制强，不能推广到别的 GPU。
  - **FlashMLA**：面向 MLA 的 latent 缓存布局做读取与调度，主要走 decode；不是 MHA/GQA 通用替代。**backend 名 ≠ 每个阶段都用同一实现**（如 FlashMLABackend 的 EXTEND 走继承的 prefill 实现）。
- **Trade-off**：长输入短输出服务看 prefill/TTFT，短输入长输出看 decode/TPOT；split-KV 用并行换合并开销；同 backend 在不同长度/并发下表现可能不同，必须实测。
- **Failure mode**：只看单个 benchmark 换后端却忽略功能不支持；换后端不跑正确性校验（浮点误差）；把 Hopper 上的 FA3 数据当成其他 GPU 的结论。

## 面试考点

1. **Q：Attention 机制 / kernel / backend 有什么区别？**
   A：机制是模型结构（MHA/GQA/MLA）；kernel 是一段具体 GPU 程序（分块矩阵乘 + 融合 softmax）；backend 是引擎把请求元数据、KV Cache 组织好并调用合适 kernel 的适配层。所以换 backend 不改变模型权重，只改执行方式。
   追问：换 backend 要注意什么？→ 兼容性（结构/硬件/dtype/功能）+ 数值精度 + 预热后的稳态性能。
   陷阱答案：说"换 backend 会改变模型结构"或"backend 就是 kernel"——backend 是适配层，可以组合多个 kernel。

2. **Q：FlashAttention 为什么快？省了什么、没省什么？**
   A：传统实现把 n×n 分数表和权重表写回 HBM 再读回，IO 是瓶颈；FA 分块进 SRAM + online softmax，让中间矩阵不落 HBM。它省的是中间矩阵搬运，**计算量仍是 O(n²)**，长序列 prefill 依然 compute-bound。
   追问：32k 单头分数表多大？→ n²=1.07e9 个分数，2 字节约 2GiB，写读一次约 4GiB。
   陷阱答案：说"FA 把 attention 复杂度降到 O(n)"——那是线性 attention，不是 FlashAttention。

3. **Q：为什么 prefill 和 decode 需要不同的 kernel？**
   A：prefill 一次多个 Query、可摊薄 KV 读取，通常 compute-bound；decode 每个请求通常 1 个 Query、要读整段历史，memory-bound。decode 常用 split-KV 把长 KV 拆段提并行度，再合并 softmax。
   追问：split-KV 什么时候不划算？→ batch 已大/上下文短、GPU 利用率已饱和时，拆分只加合并开销。
   陷阱答案：说"decode 也靠堆算力"——decode 算力利用率低，堆算力不降 TPOT。

4. **Q：SGLang 为什么提供多个 backend，怎么选？**
   A：不同请求形状、模型结构、GPU 架构是 many-to-many 组合。先筛兼容（MHA/GQA/MLA、硬件、dtype、功能），再按服务形态测 TTFT/TPOT/吞吐/显存/正确性。可用 `--prefill-attention-backend` 与 `--decode-attention-backend` 分开指定（需共享 KV 布局）。
   追问：FlashMLA 能用在任意 MHA 模型吗？→ 不能，它适配 MLA 的 latent 缓存布局，不是通用替代。
   陷阱答案：给四个后端排固定名次——它们出发点不同（服务组织/开发效率/硬件利用/MLA 专用），脱离场景无固定优劣。
