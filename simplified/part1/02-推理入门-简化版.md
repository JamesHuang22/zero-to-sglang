## 一句话核心

推理是"给定上文预测下一个 token"的自回归前向计算，按计算特征拆成 compute-bound 的 **Prefill** 和 memory-bound 的 **Decode**，用 **Roofline model** 判断瓶颈后才知道该优化什么。

## 核心概念（只留能算账的公式）

- **训练 vs 推理**：单步数学形式相同（对词表估计概率分布），差别在"前文来源"和"能否并行"。训练一次 token 计算量 = 前向 `2N` + 反向 `4N` = `6N` FLOPs，用真实标签并行算所有位置；推理只有前向 `2N`，且必须串行逐 token 生成（步间串行、步内并行）。N 是参数量。
- **Prefill FLOPs**：`L × (24Nd² + 4N²d)`。L=层数、N=输入 token 数、d=隐藏维。线性项（投影+FFN）随 N 线性增长，注意力项 `4N²d` 随 N 平方增长——中等长度近似线性，长 prompt 时二次项加速上涨。
- **Decode FLOPs/token**：`L × (24d² + 4Sd)`。S=已生成的历史长度。注意括号里是 `d²` 不是 `Nd²`：每步只算 1 个新 token，计算量极小，但要把全部权重和 KV Cache 从显存读一遍，所以卡在带宽。
- **Roofline**：`拐点 = 峰值算力(FLOP/s) / 带宽(Byte/s)`；`AI(算术强度) = 总FLOPs / 总Bytes`。AI < 拐点 → memory-bound（性能 ≈ AI × 带宽）；AI ≥ 拐点 → compute-bound（性能 ≈ 峰值算力）。
- **实例（LLaMA-7B，A100）**：A100 312 TFLOPS、1.6TB/s → 拐点 ≈ 195 FLOPs/Byte。Prefill（N=100）AI ≈ 100，接近 compute-bound；Decode（S=100）AI ≈ 1，严重 memory-bound。A100 实测 Decode 每 token 内存流量 ≈ 15.5GB（权重 14GB + KV 1.5GB），带宽下限 `15.5GB / 1600GB/s ≈ 9.7ms`，远超其 14.4 GFLOPs 的理论计算时间。

## 行业 Best Practice

- **两个阶段分开优化**：Prefill 靠提高并行度、batch、算子融合、Tensor Core；Decode 靠量化（减权重搬运）、压 KV Cache、前缀复用（RadixAttention）。混为一谈会选错方向。
- **场景决定瓶颈**：Agent 协作每次工具调用都要重新 Prefill 累积的上下文（system prompt、历史、工具定义），TTFT 线性上涨；多轮对话每轮重算完整历史，>10 轮后 Prefill 常占响应大头。
- **成本结构**：训练是一次性大额投入，推理是持续性边际成本。原文算账：8B 模型 BF16 训练约需 90 张 H100 一天（数万美元级），而每天 100 万次（512+128 token）请求的月度推理成本可达数万美元，年累计反超训练——这正是"推理优化"能成立的经济学前提。
- **现代架构默认**（替代老 Transformer）：RoPE、GQA/MLA、RMSNorm+Pre-Norm、SwiGLU、MoE；这些在第 1 章已展开，此处只需记住它们决定了 Prefill/Decode 的算力与访存基数。

## 面试考点

1. **Q：为什么 Prefill 是 compute-bound、Decode 是 memory-bound？**
   A：Prefill 一次并行处理全部输入 token，注意力是 O(N²)，算力密集，瓶颈在 Tensor Core；Decode 每步只算 1 个 token（GEMV），算力极小，但要读完整权重 + 不断增长的 KV Cache，瓶颈在 HBM 带宽。
   追问：怎么验证一个阶段到底 bound 在哪？→ 算 AI 值和硬件拐点比，或直接 profile 看是算力利用率低还是带宽打满。
   陷阱答案：说"Decode 堆算力就快"——Decode 算力利用率很低，加算力几乎不降 TPOT。

2. **Q：Roofline model 怎么用？拐点怎么算？**
   A：拐点 = 峰值算力 / 带宽，A100 约 312T/1.6T ≈ 195 FLOPs/Byte；再算任务 AI = FLOPs/Bytes，落到拐点左侧是 memory-bound（性能=AI×带宽），右侧是 compute-bound（性能=峰值算力）。
   追问：矩阵越大 AI 怎么变？→ AI 随规模增大，数据复用率越高越偏 compute-bound。
   陷阱答案：只背公式不算账，说不出自己硬件上的拐点大概是多少。

3. **Q：训练和推理的成本结构差异为什么重要？**
   A：训练 token 计算量 6N、推理 2N，但推理是持续发生的，规模化后累计成本反超训练，所以优化单次推理的时延和显存能直接摊薄边际成本。
   追问：这怎么影响架构决策？→ 训练时就要为推理"买单"：GQA/量化感知训练（QAT）必须在训练阶段定，部署时改不了。
   陷阱答案：认为推理优化不如训练重要——训练定能力上限，推理定成本和体验，两者是闭环。

4. **Q：Agent 场景的推理瓶颈在哪？**
   A：每次工具调用都要重新 Prefill 累积的上下文（系统提示、历史、工具定义），且工具结果不断膨胀上下文，Prefill 成本持续上升；跨 Agent 等待还会放大排队延迟。
   追问：优化方向？→ 前缀缓存复用共享上下文、压缩工具结果、降低重复 Prefill。
   陷阱答案：只盯着 Decode——Agent 的主要矛盾常在 Prefill 的重复计算和上下文膨胀。
