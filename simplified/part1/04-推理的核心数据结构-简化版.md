# 04 · 推理的核心数据结构：KV Cache（简化版）

## 一句话核心

KV Cache 缓存每层每个 token 的 K、V，让 Decode 不用对历史 token 重复投影，代价是显存随序列长度**线性增长**，成为长上下文 + 高并发下的主要显存瓶颈。

## 核心概念（只留能算账的公式）

- **来源**：Prefill 一次性算整段输入的 K、V 并缓存；Decode 每步只算新 token 的 Q/K/V，新 K、V 追加进缓存，Q 用一次就丢（**Q 不缓存**，因为后续步骤不复用）。各层权重不同，所以 KV Cache 按层分开存。
- **显存公式（核心，会算账）**：
  `KV_bytes = B × T × L × 2 × n_kv × d_h × s`
  - B=batch（并发请求数）、T=每请求 token 数、L=层数、**2=K 和 V 两份**、n_kv=KV 头数、d_h=每头维度、s=每元素字节数（BF16=2）。
  - 每个因子翻倍，KV Cache 就翻倍。Decode 每生成 1 个 token 新增 `B × 1 × L × 2 × n_kv × d_h × s`，随输出长度线性累积。
- **实例（Qwen3-4B，L=36，n_kv=8，d_h=128，BF16）**：单请求 100 token 上下文 → KV Cache ≈ 14.06MB；每生成 1 token 新增 ≈ 0.141MB；4K 上下文 ≈ 0.56GB，32K ≈ 4.50GB；**8 个满 32K 请求 ≈ 36GB**（还没算权重）。而 4B 模型权重本身 ≈ 7.45GB——**短上下文时权重主导，长上下文/高并发时 KV Cache 反超权重**。
- **生命周期**：`分配 → Prefill 批量写入（命中前缀可跳过）→ Decode 反复读+追加 → 释放回空闲池或保留复用`。真实系统里前缀缓存/分页/淘汰会让"追加"不再是连续增长的显存。

## 行业 Best Practice

- **KV Cache 是持久驻留、按 token 近似线性增长的，激活值是临时流动的**——所以长期显存压力来自 KV Cache 而非激活。这是理解"为什么推理系统整天优化 KV Cache"的根。
- **naive 连续分配的四个坑**（多请求下）：① 显存碎片与预留浪费（按最大长度预留 = 提前占用）；② 无法共享重复前缀（system prompt 重复存）；③ 调度/回收/扩容复杂（可能触发搬移复制）；④ 不利于 continuous batching（变长请求要按最大长度填充，浪费算力）。
- **现代替换方向（此处只点题，Part II 第 4/7 章展开）**：细粒度 **block/page 分页**管理 + 前缀共享（PagedAttention / RadixAttention），解决上述四坑。GQA/MLA 则从"源头"减少 n_kv/d_h，压缩 KV 总量。
- **CPU offload 的 trade-off**：把 KV 放 CPU 能缓解显存、扩容量，代价是 Decode 每步读 KV 的带宽变慢、吞吐下降（原文测试题原话方向）。

## 面试考点

1. **Q：KV Cache 显存公式，为什么乘 2？**
   A：`B × T × L × 2 × n_kv × d_h × s`，2 是因为每个 token 每层要存 K 和 V 两份张量。每个因子翻倍，显存就翻倍，其中 T、B 是运行时变量，L/n_kv/d_h 是模型架构变量。
   追问：架构上怎么压？→ GQA/MLA 减少 KV 头数或低秩压缩 KV 维度。
   陷阱答案：漏掉 2（只算一份），或把 n_kv 当成注意力头数——GQA 下 KV 头数远小于 Q 头数。

2. **Q：为什么只缓存 K、V 不缓存 Q？**
   A：Q 只用于当前 token 这一次 Attention，Decode 下一步不复用；K、V 要被后续每个新 token 反复读取做注意力，缓存才省下重复投影。
   追问：Prefill 的 Q 呢？→ 也是当次用完即弃，不落盘。
   陷阱答案：说"Q 不重要所以不存"——是"不复用"所以不存，不是不重要。

3. **Q：一个 4B 模型（L=36, n_kv=8, d_h=128）8 并发、每请求 32K 上下文，KV Cache 多大？**
   A：`8 × 32768 × 36 × 2 × 8 × 128 × 2 bytes ≈ 36GB`，超过 4B 权重本身的 7.45GB，说明此时 KV Cache 才是显存主导，限制并发和上下文。
   追问：这怎么影响部署？→ 显存先给权重和 KV Cache 预留，KV 越吃显存，能塞的并发越少。
   陷阱答案：只报权重显存、忽略 KV Cache，导致容量规划翻车。

4. **Q：naive 连续分配 KV Cache 有什么问题？**
   A：碎片/预留浪费、重复前缀无法共享、调度回收复杂、不利于 continuous batching（变长请求要填充到最大长度）。根因是把每个请求当成一块独立连续显存。
   追问：现代引擎怎么解决？→ 按 block/page 分页 + 前缀共享（PagedAttention/RadixAttention）。
   陷阱答案：说"连续分配没问题，反正显存够"——碎片和填充浪费在长尾长度下会被放大。

5. **Q：KV Cache 放 CPU 内存，收益和代价？**
   A：收益是缓解 GPU 显存、扩上下文容量、省成本；代价是 Decode 每步读 KV 从 HBM 带宽掉到 PCIe/主存带宽，吞吐下降、延迟上升。
   追问：什么场景值得？→ 长上下文、低频访问、对延迟不敏感的场景（如冷数据分层）。
   陷阱答案：只看到省显存，忽略 Decode 是 memory-bound，放慢速存储会直接拖垮 TPOT。
