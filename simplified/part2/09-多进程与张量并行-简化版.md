## 一句话核心

单卡装不下或扛不住目标负载时，用多进程（Multi-process）组织多卡协作、用张量并行（TP）把同一层权重切到多卡共同计算同一批输入，两者配合才能既放得下模型、又算得对。

## 核心概念（只留能算账的公式）

**什么时候需要多卡——先算权重显存**：
`权重显存 ≈ 参数量 × 每参数字节数`。Qwen2.5-32B 用 BF16：`3.2×10^10 × 2B ≈ 64 GB`。一张 A100 80GB 放得下权重，但还要 KV Cache（随 token 总数增长）、激活值/工作区、通信缓冲、CUDA Graph 缓冲——**"权重装得下 ≠ 目标负载下不 OOM"**。1.6T 参数 BF16 ≈ 3.2 TB，必须多卡。

**Multi-process vs TP**：
- **Multi-process** = 系统组织方式：多进程绕过 Python GIL，组件有 API Server / Tokenizer / Detokenizer / Scheduler / Engine；一个 rank = 一张 GPU = 一个进程。
- **TP** = 模型并行策略：把同一层权重/词表切到多个 rank，共同完成同一批输入的计算。

**切分方式与通信**：
- **Column Parallel（按输出维切）**：qkv_proj、gate_up_proj。输入完整复制，各 rank 算部分输出。
- **Row Parallel（按输入维切）**：o_proj、down_proj。输入是上层切好的局部结果，各 rank 算局部贡献后 **All-Reduce 求和**：`Y = Y_0 + Y_1 + … + Y_{p-1}`。
- **Vocab Parallel（按词表维切）**：Embedding / LM Head，词表 pad 到整除 tp_size；Embedding 用 all_reduce、LM Head 用 **All-Gather 拼接**：`Y = cat(Y_0,…,Y_{p-1})`。
- **注意力头**：Q 几乎总按 head 切（要求 num_heads % tp_size == 0）；KV 若 `num_kv_heads ≥ tp_size` 按 head 切，否则**复制 KV head**让多 rank 共享。

**三层通信**：
- **ZMQ**：rank0 与 Tokenizer/Detokenizer 之间传请求，rank0 用 Pub/Sub 广播给其他 rank（只 rank0 对外，避免消息错乱）。
- **Gloo（CPU 进程组）**：启动 barrier、NCCL Unique ID 广播、每轮消息条数同步。
- **NCCL / PyNCCL（GPU 张量）**：All-Reduce、All-Gather。

**一致性**：`相同请求集合 + 相同请求顺序 + 相同 token/长度状态 = 可协同计算的 Batch`。各 rank 独立更新本地调度状态，靠 rank0 广播保证输入一致，靠集合通信保证输出正确。

## 行业 Best Practice

- **切分原则**：小层（RMSNorm 等）完整复制；大权重（线性层/词表）按维度切；先 shard 再 merge（q/k/v→qkv_proj、gate/up→gate_up_proj），否则破坏本地配对。
- **流式加载权重**：边读 safetensors 边切分，峰值 CPU 内存控制在一个完整 tensor + 小 merge buffer，避免加载尖峰。
- **TP 翻倍 ≠ 显存减半/速度翻倍**：小层复制、KV head 可能复制、通信（All-Reduce/All-Gather）有开销。TP 收益取决于模型大小、batch、卡间带宽。
- **mini-sglang 只支持 TP**；真实 SGLang 另有 DP（数据并行）、PP（流水线并行）、EP 等，选型要先算显存再看通信。
- **failure mode**：该 All-Reduce 的地方漏通信 → 输出严重偏差；多 rank 各自直接连 Tokenizer → 消息错乱；KV head 数 < tp_size 还硬切 → 单 head 被切坏。

## 面试考点

1. **Q：TP 和 DP、PP 的区别？**
   A：TP 把同一层权重切到多卡共同算同一批输入，卡间频繁通信，单请求延迟可能降低；DP 是不同卡跑不同请求，通信少但每卡要完整模型；PP 按层分段流水线，通信少但有 pipeline bubble。mini-sglang 只实现 TP。
   追问：什么时候 TP 收益最好？→ 模型大（放不下/算不动）、batch 足够、卡间 NVLink 带宽高时。
   陷阱答案：把 TP 当"一定能线性加速"——通信开销会吃掉收益。

2. **Q：Column Parallel 和 Row Parallel 的通信位置分别在哪？**
   A：Column 切输出维（qkv_proj、gate_up_proj），输入完整、输出是部分结果；Row 切输入维（o_proj、down_proj），各 rank 算局部贡献后 All-Reduce 求和得到完整输出。两者成对出现（先 column 后 row），中间才有局部状态流动。
   追问：漏了 All-Reduce 会怎样？→ 后续层拿到的不是原模型结果，输出严重偏差。
   陷阱答案：把 All-Reduce（求和）和 All-Gather（拼接）用反。

3. **Q：GQA 模型 num_kv_heads < tp_size 时 KV 怎么切？**
   A：KV head 切不动了（单 head 不能再分），只能复制 KV head，让多个 rank 共享同一份 K/V。Query head 仍可切。这也是 TP 翻倍显存不严格减半的原因之一。
   追问：词表大小不整除 tp_size 怎么办？→ pad 到整除再均分，logits 拼回后截断到真实词表大小。
   陷阱答案：说"KV 头也随便切"——num_kv_heads < tp_size 时硬切会破坏单 head 语义。
