## 一句话核心

一条请求从 API Server → tokenizer → scheduler → engine → detokenizer → 流式返回的完整链路；**uid 贯穿所有阶段**，把每个阶段的状态和结果串回对应客户端。

## 核心概念（只留能算账的公式）

- **五个环节 + 三次表示转换**：文本 →（分词）→ token ids →（模型+采样）→ 新 token →（反分词）→ 文本。请求标识（uid）全程不变。
- **scheduler vs engine**：scheduler 决定"算谁"（选请求、组 batch、检查 KV Cache 容量/前缀命中）；engine 负责"怎么算"（前向得到 logits + 采样出 token）。mini-sglang 里两者同进程，是函数调用，不是跨进程消息。
- **logits vs 概率 vs 采样**：logits 是词表每个候选的未归一化分数；softmax 转成概率；greedy 直接取 argmax（不必真算 softmax，顺序不变），带温度才先缩放再 softmax 后按概率抽。
- **detokenizer 必须保留每条请求的解码状态**：一个 token 可能只含某个字符的部分字节，逐 token 独立解码会出 `�`；要结合历史判断哪些文字已完整，只放行新增可输出部分。
- **多进程收益**：① 重叠工作（tokenizer 处理 B 的输入时 scheduler 继续推进 A）；② 多卡协同（每卡一个 scheduler worker，但必须对同一批请求调度一致）；③ 按瓶颈扩组件；④ 排查边界清晰。代价：通信 + 状态同步 + 故障恢复。
- **取消链路**：客户端断开 → API Server 发 `AbortMsg` → tokenizer 转 `AbortBackendMsg` → scheduler 从队列/运行集合移除并释放资源。

## 行业 Best Practice

- **流式输出是标配**：改善 TTFT 和体验（用户边看边等），几乎不存在非流式客户端；SSE 分块返回，`[DONE]` 是接口约定而非 SSE 标准。
- **单进程异步 vs 多进程**：单进程也能用线程/异步 IO/异步 GPU 执行实现并发；多进程便于分开管理流程，但不会消除单请求内部依赖。
- **扩容前先定位瓶颈**：GPU 没活干（就绪请求不足）时加 tokenizer worker 才有意义；瓶颈在 GPU 时加 tokenizer 只积压队列。
- **Failure mode**：漏传/改错 uid → 结果串到别的连接；detokenizer 不保留状态 → 输出乱码；客户端断开后不取消 → GPU 为无人接收的请求继续烧算力。

## 面试考点

1. **Q：scheduler 和 engine 分别负责什么？必须在不同进程吗？**
   A：scheduler 决定算谁（选请求、组 batch、管 KV Cache 容量），engine 决定怎么算（前向+采样）。mini-sglang 里同进程、函数调用；模块边界≠进程边界。
   追问：为什么同进程还能说它们是两个模块？→ 职责不同，后续可以各自拆进程/扩机器。
   陷阱答案：说 scheduler 做矩阵运算、engine 做排队——正好反了。

2. **Q：detokenizer 为什么要保留状态？逐 token 独立解码会怎样？**
   A：token 可能只含字符部分字节（尤其中文/emoji），独立解码产生 `�` 替代字符；保留状态才能判断哪些字节拼完整、只输出新增安全部分。
   追问：这和 tokenizer 有关系吗？→ 是反方向，tokenizer 编码、detokenizer 解码，两者都要保留各自状态。
   陷阱答案：说"每个 token 就是完整一个词，拼起来就行"。

3. **Q：多进程和单进程异步并发，怎么选？**
   A：多进程重叠 CPU/网络/GPU 工作、边界清晰、可独立扩容，代价是通信和状态同步；单进程异步靠 await 让出，无跨进程开销但共享故障域。生产 SGLang 是混合：HTTP+Tokenizer 同进程，scheduler/detokenizer 子进程。
   追问：长 prompt 请求大量涌入，瓶颈可能在哪？→ 分词 CPU，先加 tokenizer worker。
   陷阱答案：认为多进程一定更快——通信本身是开销，要按瓶颈选。

4. **Q：用户中途断开，GPU 一定立刻停吗？**
   A：不一定。断开只关连接，后端要靠取消消息（AbortMsg→AbortBackendMsg）通知 scheduler 移除请求并释放资源；已提交 GPU 的计算不会瞬间消失，是协作式取消。
   追问：取消消息漏传会怎样？→ 请求继续生成，KV Cache 和显存被无人请求占用。
   陷阱答案：说"HTTP 断开就自动停止推理"。

5. **Q：streaming 优化了什么指标？**
   A：优化 TTFT 和用户体感（更早看到首段内容）；不减少前向次数、不提升 TPOT 或吞吐。
   追问：非流式等于阻塞服务吗？→ 否，该请求等待时其他请求仍可推进。
   陷阱答案：说"流式让生成更快"。

### 代码在干嘛（不抄代码）

- `server/api_server.py`：`new_user()` 发 uid；`listen` 协程统一收 `UserReply` 按 uid 存入结果缓冲、`event_map` 唤醒对应协程；`/v1/chat/completions` 发 `TokenizeMsg` 并返回 `StreamingResponse`。
- `tokenizer/server.py`：`TokenizeMsg` → 分词 → `UserMsg` 发给 scheduler；取消时 `AbortMsg` → `AbortBackendMsg`。
- `scheduler/scheduler.py`：`normal_loop` 四步（收消息 → `_schedule_next_batch` 组 batch → `_forward` 调 engine → `_process_last_data` 处理结果/发 `DetokenizeMsg`）。
- `engine/engine.py` + `sample.py`：`forward_batch` 算 logits → `sample`（greedy 直接 argmax，带温度走 softmax+抽样）→ 结果拷回 CPU。
- **改错会出什么问题**：uid 传错/复用 → 结果串线；组 batch 只组 prefill 不 fallback 到 decode → 生成中的请求卡死；detokenizer 不保留状态 → 输出乱码；漏发 `AbortBackendMsg` → 取消不生效、资源泄漏。
