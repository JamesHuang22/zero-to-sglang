## 一句话核心

开源协作的第一课不是技术而是责任：**对自己的代码负责、沟通说人话、性能优化先 profile**，三者本质都是"尊重 reviewer 和后来者的时间"。

## 核心概念（只留能算账的公式）

本章没有数学公式，但有两条"能算账"的工程判断，面试和日常都用得上：

- **3% 原则**：要优化的那段如果只占总耗时 3%，把它优化到零，端到端也只快 3%。所以动手前先回答"这段在真实负载下占多少时间"，答不上来就先去测——一小时 profiling 能省两周瞎改。这和第 2 章 Roofline 的"先定位瓶颈再优化"是同一个思维。
- **AI 时代的责任转移**：AI 写 500 行只需 30 秒，但 reviewer 读 500 行、判断它对不对，还是要几小时。代码产出成本暴跌，审查成本没变，所以"提交前自己读过并答得上来"是底线。

三条自查（提 PR 前逐条过）：① 这个 PR 解决的 motivation 是什么？② 成果怎么复现？③ 随便抽一个函数，删了它会怎样？答不上来就别提交。

## 行业 Best Practice

- **性能 PR 三件套**（缺一不可）：PR 前后对比数据、可复现命令、profile 证据（别人要的是"为什么快"，不是"快了 12%"）。正确流程是 `profile → 找瓶颈 → 改 → 再 profile 对比`。
- **沟通说人话**：issue/PR/review 回复用自己的话写，不要整段贴 AI 生成内容。AI slop 的特征是"两百字里有用的十五个字"，维护者看到 AI 味回复会直接怀疑"这个 PR 也是生成的，本人没读过"，信任一旦打折扣，review 成本翻倍。
- **坏 PR 清单（反向避坑）**：AI 生成且本人没读过的大 PR；性能 PR 不带数据；不经设计就重构核心模块、侵入性过强；未经讨论就加依赖/改默认参数；同时开十个 spam PR。
- **好 PR 的样子**：小、完整、真正解决一个 existing issue、有验证。顺序是"先了解 → 后提问 → 最后贡献"。
- **开源心态**：贡献不限于代码，文档、翻译、复现 benchmark、帮人定位 issue 同等重要；不欢迎的是把 PR 数量当目的、把开源当刷简历工具的人。

## 面试考点

1. **Q：你拿到一个"优化了 20%"的 PR，会追问什么？**
   A：先问 baseline 是什么、在什么负载下测的，再看有没有 profile 证据说明瓶颈确实在被改的那段。没有可复现命令和前后对比数据，20% 不可信。
   追问：如果作者说"顺手改的没记录"，你怎么办？→ 要求补齐基准，否则不能合入。
   陷阱答案：只看最终数字"快了 20%"就通过——没有基准和 profile，数字无法归因。

2. **Q：为什么性能优化一定要先 profile？**
   A：因为大部分优化都发生在只占很小比例的耗时上（3% 优化到零也只快 3%）。先 profile 找到真正的热点，再决定改哪里，投入产出比才成立。
   追问：profile 工具会看什么？→ 时间占比、kernel 耗时分布，判断是 compute-bound 还是 memory-bound（对应第 2 章 Roofline）。
   陷阱答案：凭直觉"觉得这段慢"就直接改——直觉热点经常不是真热点。

3. **Q：AI 写代码时代，代码审查有什么新挑战？**
   A：写代码成本暴跌但审查成本没变，容易产生大量作者本人没读过的大 PR，把工作量转嫁给 reviewer。所以社区要求作者自己先读、能解释动机和函数作用。
   追问：怎么识别 AI slop 的回复？→ 包装话多、信息密度低，一两句能说清的事写成一大段。
   陷阱答案：认为"AI 写得多所以贡献多"——数量不等于质量，反而稀释 review 资源。

> 本章是软技能章，面试点来自原文 + 通用工程实践，未做额外外部检索。可参考的最近技术来源：[SGLang Benchmark & Profiling（Nsight/NVTX 用法）](https://docs.sglang.io/docs/developer_guide/benchmark_and_profiling)。
